KPI Master & Weight

HR maintains the list of things being assessed per job grade. Every row carries a target type and an HR-locked raw weight. Supervisors never write to this table — they only browse the active rows of their subordinates' grade before copying a row onto a review sheet.

Two columns deliberately absent

The grid never carries used_in_sheet_count — counting usage per row would turn one search into N+1 queries. That number appears only inside the Edit and Delete modals. Raw weights are also free positive numbers: they are not required to add up to 100, because the percentage share is computed by the sheet, not here — the running total above is a reading aid only.

The search contract accepts exactly three inputs — job_grade_id, is_active and sort_by (created_at · job_grade_id · is_active) — so this toolbar carries no free-text box and no target-type filter. Nothing is filtered client-side either; the earlier free-text search was outside the contract and has been removed.

Edits do not travel into running sheets

A change takes effect immediately for future copies, but never touches review-sheet lines that already copied this row — each sheet uses its own copy. Every field is optional on update, yet an empty payload is a 422: send at least one.

Delete item

DELETE /kpi-items/{id} — a soft delete: the audit columns are stamped, the row survives.

Usage is information, not a gate

This row is used by running sheets — that does not block anything.

Deleting and the AKTIF/NONAKTIF flag are two independent mechanisms: this call does not touch the status flag. To keep the row but take it off the supervisor's picking surface, set its status to NONAKTIF in Edit instead.
