Change History

One read-only grid across every company setting, newest first — not a history per setting. The question people actually ask during a dispute is what changed last month, and who, so the toolbar offers four filter axes instead of a tab per menu. This screen is the control that remained after second-person approval was dropped from setting changes.

Carried in from a settings row

The Setting filter arrived pre-filled from the History link on a settings grid row — . Opening the history of one row does not open a second menu. Pressing an actor's name on a row, by contrast, does not set the actor filter: the answer never carries an employee_id, so there is nothing to carry.

The Menu column is derived on this screen from the setup_code prefix — no server field carries it. Before is empty exactly on version 1 and is computed by the server, never by the client. Actor has three shapes, and they are told apart by the pair employee_id+nik, not by employee_id alone: testing the id by itself would let an anonymised row pass as a system row — the opposite conclusion.
Two things are always enforced by the server and can never be sent from here: there is no locked-row filter — platform rows stay visible to the two top roles, because what is shown is the platform changing itself (accountability), not a value they may set — and employee_id is stripped from every answer.
No buttons, without exception, and no toast: this menu has no write door at all. Pagination is mandatory from birth. The page opens at the contract's default size of 25 (the contract's ceiling is 100). Sorting is created_at DESC by default, itself a deliberate deviation from the ascending house rule, and a column outside the sort whitelist is refused 422 and recorded as a parameter-injection attempt.
The Actor filter is fed by the employee picker owned by employee-service — not a settings endpoint, and not claimed to exist by the settings documents. It is optional, so it does not block anything, but its chain is not verified live either.
