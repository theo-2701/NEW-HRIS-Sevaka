Lifecycle & lock gates

Reference only — the server re-evaluates every gate at submit time.

Lifecycle — payroll_period_status
Four states, one forward path and one backward path. HANDED_OVER is absolutely terminal — the only correction after it is an adjustment in the next period.
CALCULATED
Born when the officer runs the period, in Salary Processing.
→ REVIEWED
Officer marks it reviewed. This is where the period arrives in this menu.
→ LOCKED
Checker locks it — three gates plus maker–checker, all evaluated server-side.
→ HANDED_OVER
Authorised for the client system once zero employee-subject findings are open.
Backward — reopen, reason mandatory: LOCKED → REVIEWED · LOCKED → CALCULATED · REVIEWED → CALCULATED. Only the holder of locked_by on that row may do it, so in practice a reopen starts from a locked period; a REVIEWED row that never carried a lock has no eligible caller. Never available from HANDED_OVER.
The three lock gates
Evaluated in order, so the server reports the first failure. payroll.allow_lock_before_cutoff never waives any of them — it only allows an earlier lock moment.
Gate 1 · Time reconciliation
time_reconciliation_completed_at is filled. Fails with 422 PAY_LOCK_BLOCKED_TIME_MISMATCH.
Gate 2 · Finance deduction pull
Loan, cash-advance and receivable deductions pulled in full — finance_deduction_pull_completed_at is filled. Fails with 422 PAY_LOCK_BLOCKED_FINANCE_INCOMPLETE.
Gate 3 · Param snapshot
All ten cnf_payroll_period_param_snapshot rows frozen (10/10) — derived, not stored. Fails with 422 PAY_LOCK_BLOCKED_NO_PARAM_SNAPSHOT.
