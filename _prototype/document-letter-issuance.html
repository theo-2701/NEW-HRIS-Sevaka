Letter Issuance

Issue letters from drafts that have already been approved — one at a time, or in bulk. The third and separate sub-module: the HR staff who issue letters have zero access to the draft library (DOC-81).

PROB-SERVICE-356 — HIGH, OPEN

This screen has no menu row in the architecture blueprint menu map / mst_menu. The contract is complete but nobody can reach the screen through the HRIS menu until the row is registered in auth-service (mst_menu + map_access_menu). Stated, not invented.

This page has no grid of individual letters — on purpose

Approving (A11) and cancelling (A12) a single letter are really executed on the document detail screen (A4, in Company / Employee / Other Files), where {letter-id} is carried from the letter block. Here they are only narrated and demonstrated.

One response code, two shapes

Both branches answer 201. Gate off → TERBIT, with letter_no, verification_code, issued_at and document_id filled. Gate on → MENUNGGU_PERSETUJUAN, all four null. Different payload, never a different code.

Actors

ROLE_HR_STAFF issues but never approves · ROLE_HR_MANAGER issues and approves · ROLE_SUPER_ADMIN is the fallback ladder for approval and does not issue · approver ≠ submitter is enforced with 403, and cannot be expressed as a database CHECK.

What the grid row deliberately omits

No items and no summary — counting them per grid row is expensive; they live in the report (A13b). There is also no “only the batches I submitted” filter, no recipient filter and no template-name keyword: the effective scope is the whole company.

Four fields deliberately absent

letter_target · signer_scope · category_id — all owned by the template and derived by the server — and letter_no, minted by the server at TERBIT. The draft body is never sent from the client either.

recipient_employee_ids[] — duplicates break a unique constraint (422). Whether each employee actually exists is not validated at submit time; it surfaces as GAGAL when the task runs.

Frozen by the server

template_version_id is frozen at submit time · recipient_count is counted · no submission note field exists. A partial failure writes zero rows.

Decide on batch

POST /letter-batches/{batch-id}/approve — decision is exactly DISETUJUI or DITOLAK. There is no rejection-note field.

Approver ≠ submitter

Enforced with 403 after the state check. A batch already decided answers 422, not 409 — this is a business rule, not a write collision. On approval the recipient list is frozen and the background worker becomes eligible to run.

Batch report

GET /letter-batches/{batch-id} — the three counters are computed, and the report stays openable after the queue has finished.
