Document Category Settings

Two levers decide how open every document in a category is: the category markers, and the category → reader-role map. Both end at one second-hands gate and one has_pending_change flag — two proposals on the same category cannot coexist (409).

Tightening and loosening are two different stories

Tightening (deactivate, shorten access, narrow readers) takes effect immediately: 200, plus one log_document_category_change row per moved attribute. Loosening (e.g. shortening retention, widening readers) only gives birth to a proposal: the response still carries the values in force, has_pending_change=true, and a second attempt is 409. Flattening them into one branching form would violate G3.

Five fields deliberately not accepted

category_origin · confidentiality_class · is_active · id · has_pending_change — sending any of them returns a named-field 422. The constraint forces category_origin=PERUSAHAAN and confidentiality_class=BIASA for anything created here; INDUK categories are seeded, never born from an address.

Tighten category

PUT /document-categories/{category-id} — a tightening direction takes effect the moment it is saved. No second pair of hands.

Deactivating replaces delete — Document Service has no Delete (DOC-37). The row leaves the default list; the toggle above the grid brings it back into view.

Other directions that also tighten

Lengthening retention, shrinking max size, narrowing allowed MIME types, hiding from self-service, removing a reader role. All of them land on the same immediate path: 200 + one log row per moved attribute + event KATEGORI_DIUBAH.

Loosen category — raises a proposal

Same address, different story. The answer is 200 (never 201) and it carries the values still in force.

Shortening the retention loosens the category.

Impact — safeguard 1 of 3

Documents affected: 0. The server computed this number; the proposer sends it back as acknowledged_impact_count. The approver sees it again and it must be identical (safeguard 3). Omitting it when a loosening attribute is present is a 422.

Decide on proposal

POST /document-categories/{category-id}/approve — ROLE_SUPER_ADMIN only, and a different person from the proposer. Signed in as Rina Amelia · NIK 20210715.

Echoed back in the response, then gone — nothing is stored.

What each branch does

SETUJU: the values are applied, one log_document_category_change row per attribute (created_by=proposer, approved_by=approver), event KATEGORI_DIUBAH, flag cleared. TOLAK: the proposal is thrown away and the flag is cleared — zero rows born. Zero Kafka, zero workflow engine.

Reader roles

PUT /document-categories/{category-id}/readers — the whole list is replaced, never added to or removed from one by one.

Impact

Documents affected: 0 — sent back as acknowledged_impact_count. The proposal is gated by the same A6d door, and the flag sits on the category row. Nothing in map_document_category_reader moves until the approval lands.
